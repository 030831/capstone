# 인지적 정렬 검사기 (프로토타입 v3) — 웹

팀 내부 검토·중간 발표 데모용. 백엔드·로그인·LLM 없이 브라우저에서만 동작한다.
개념 그래프(`../graph/graph_v0.yaml`, 39노드/72엣지) 위에서 "이 문제가 이 학생에게 준비된 문제인가"를 판정한다.
판정은 4종: **COLLISION(확인이 필요한 선수 개념) / NEEDS_REVIEW(아직 확인하지 않은 기록) / ALIGNED / TOO_EASY**.

## v2 → v3 변경 (2026-11-07 사용자 지시서)

v2의 문제: **기록 없음을 미시작으로 취급**했다. IEP는 확인한 것만 기록하는 문서이므로
"기록에 없음"은 "아직 다루지 않았다고 확인함"과 다르다. 이에 따라:

- **상태 4종·판정 4종.** `미확인(unknown, 기록 없음)`을 `미시작(not_started, 명시)`과 구분하고
  미확인이 있으면 `NEEDS_REVIEW` 판정으로 "기록을 확인해야 한다"고만 알린다(단정하지 않는다).
  Python 엔진과 TS 엔진이 같은 판정을 내리는지 공유 fixture(`../tests/fixtures/shared_cases.json`,
  25건)로 검증한다. 엔진 스펙: `../docs/SPEC_collision_checker.md` §3.
- **IEP 초안과 확정 데이터 분리.** "초안 채우기"가 학생 데이터를 바로 고치던 것을
  **붙여넣기 → 변경 내용 미리 보기 → 항목 선택 → 선택한 내용 적용 → 1회 되돌리기** 흐름으로
  바꿨다. 미리 보기만으로 학생 상태·localStorage·검사 결과가 바뀌지 않는다.
  혼재 문장("할 수 있지만 못함")·"못함"·범위가 구분 안 되는 서술("두 자리 수 덧셈")은
  자동 변경 없이 "확인 필요"로만 나열한다. "선수까지 숙달"도 같은 미리 보기 흐름.
- **문제 개념 확정 흐름.** "이 문제에서 다루는 개념"(선수는 엔진이 계산)을 교사가
  "개념 확인" 버튼으로 확정해야 검사가 실행된다. 문제 글·개념이 바뀌면 확정이 풀린다.
  후보("문제에서 찾은 개념 후보")는 검사에 자동 반영되지 않고, 검사 후 입력을 고치면
  결과 카드에 "이전 입력의 결과"로 표시된다. 후보 규칙도 정비: 명시적 수식("8+5", "13−5")만
  숫자 규칙 적용(문항 번호 조합 금지), 우선도 순 상위 6개, **15−3 ≠ 13−5**(받아내림 구분),
  합이 10이면 10의 보수·10을 넘으면 받아올림.
- **반 일괄 검사 가드.** 검사한 문제만 반 검사에 쓴다(초안과 혼합 금지). 예시 문제 자동
  대체 제거. 기록이 없는 학생은 "아직 확인하지 않은 기록"으로 구분해 센다.
- **결과 문구 정리.** "지금 딱 맞는 문제" 같은 보장 표현 제거 → 확인·기록 중심 문구
  ("확인이 필요한 선수 개념이 있어요" 등). 노출 순서: 판정 요약 → 확인할 선수/미확인 기록 →
  교사 동작(기록 확인·문제 수정·반 검사) → 자세히 보기(접기). 구현 설명(LLM 예정 등)은
  기본 화면에서 제거.
- **저장 v2·접근성·반응형.** 학생 상태·현재 학생·작성 중 문제·확정 개념·표면 속성 복원
  (localStorage 형식 버전 2, 과거 형식 이전: 빠진 항목은 미확인). 저장 실패 시
  "이 브라우저에 저장하지 못했어요" 표시. 모달 포커스 트랩·버튼 복귀·배경 inert·Esc.
  색 아닌 텍스트로 상태 구분, 회색 글자 대비 4.5:1 이상. **1,024px 최소 폭 제거** —
  390/768/1280 확인, 표는 표 영역 안에서만 가로 스크롤.

배경은 `docs/SPEC_web_prototype.md` §0·§0-b·§0-c와 `CLAUDE.md` 참조.

## 실행

```bash
cd web
npm install
npm run graph:json   # ../graph/graph_v0.yaml -> src/data/graph_v0.json (YAML 은 수정·복사하지 않음)
npm test             # 엔진 + draft + state + 컴포넌트 흐름 테스트 (vitest)
npm run build        # tsc 타입 검사 + dist/ 생성
npm run dev          # 개발 서버
```

`dist/index.html` 은 `file://` 로 그대로 열어도 동작한다. Chrome 이 file:// 에서 `type="module"` 스크립트를 막기 때문에
`vite.config.ts` 의 작은 플러그인이 번들을 IIFE 단일 파일로 내고 HTML 의 `type="module"`/`crossorigin` 을 제거한다.
스크린샷·자동 검사 재생성: `node scripts/screenshots.cjs` (playwright 전역 설치 사용).
검사 항목: 콘솔 에러 0, **금지어 0(발견 시 exit 1)**, 모달 포커스, 390/768/1280 레이아웃.

## 화면

1. **메인(초기)** — 문제 글 textarea + 빈 결과 카드.
2. **메인(입력 중)** — 문제 글을 적으면 "문제에서 찾은 개념 후보" 칩(근거 표시). 눌러서 담고
   **"개념 확인"** 을 누르면 "검사에 사용할 개념"이 확정된다. 검색·전체 목록은 "직접 고르기" 접기.
3. **메인(검사 후)** — 판정 배지(확인 중심 문구) + 범위 안내 + 이 문제의 개념·문제 글 +
   "아직 확인하지 않은 기록"(선수/이 문제의 개념 구분) + "확인이 필요한 선수 개념"(상태 표시) +
   soft 참고 + "지금 바로 다룰 수 있는 개념"(COLLISION 만) + 교사 동작 버튼 3개.
   설명 문장·판정 코드·근거 코드·학습 계보는 "자세히 보기" 접기 안. 입력이 바뀌었으면
   "이전 입력의 결과" 표시.
4. **학생 현행수준 모달** — IEP 붙여넣기 → **변경 내용 미리 보기**(현재 상태·제안 상태·근거 문장·적용 선택) →
   선택한 내용 적용 → 적용 되돌리기(1회). 확인 필요 항목은 자동 변경 없이 이유와 함께 나열.
   그룹별 접힌 표는 상태 4택(미확인/미시작/형성 중/숙달). localStorage 저장(실패 시 안내).
5. **반 일괄 검사 모달** — 검사한 문제 상단 표시 + 학생별 판정 표(미확인 기록 열 포함).
   검사한 문제가 없으면 안내만. 행 클릭 시 해당 학생으로 전환.

## 룰 기반 제안 (`src/data/draft.ts`)

- `suggestConcepts(문제 글)`: ① 명시적 수식(연산 기호·"더하기/빼기/곱하기" 단어)과
  수량 2개 + 연산 동사가 함께 있을 때만 숫자 규칙 적용(문항 번호·문맥 숫자 조합 금지)
  ② 키워드 규칙은 우선도(수식 3 > 좁은 키워드 2 > 넓은 키워드 1) 순 상위 6개, 동률만 ID 정렬
  ③ "15−3"은 받아내림 없는 (십몇)−(몇), "13−5"는 받아내림 — 구분 ④ 합이 10인 한 자리 덧셈은
  10의 보수, 10을 넘으면 받아올림. 후보는 어디까지나 후보(확정은 교사).
- `draftIepFromText(문장, 현재 상태)`: 문장 단위로 제안(`proposals`)과 확인 필요(`needsReview`)를
  나눠 반환한다. 상태 표현이 없는 문장은 건너뛴다. 긍정·부정 혼재·"못함"·범위 구분 불가·
  문장 간 충돌은 needsReview 로 보류한다. "도움 없이 해결"은 숙달, "도움 받아 해결"은 형성 중.
- 두 함수 모두 결정적이고 판정 엔진에 영향을 주지 않는다. 테스트는 `src/data/draft.test.ts`.

## 엔진 포팅 시 주의점 (`src/engine/`)

- Python `checker/engine.py`, `explain.py` 와 같은 의미(2026-11-07 개정판: 상태 4종·판정 4종).
  설명 문장 템플릿과 조사(josa) 로직도 동일하며 테스트로 고정했다.
- 판정 순서 고정: gapHard(명시적 미확보) → COLLISION, unknownHard/unknownRequired → NEEDS_REVIEW,
  R ⊆ M → TOO_EASY, 나머지 → ALIGNED. unknown 은 gap 목록과 분리.
- `suggestedNext` 는 gapHard 중 hard 선수가 **실제로 모두 mastered** 인 노드만(선수에 unknown 이
  있으면 제외). 정렬: (R 까지 hard 최단거리, ID).
- `check` 는 빈 requires 를 DataError 로 거부한다.
- 테스트 9번: 완전 확인 학생(모든 노드 명시)은 "M ∪ fringe 밖 노드 = 항상 COLLISION",
  부분 확인 학생은 "COLLISION 또는 NEEDS_REVIEW". 합성 학생은 TS 로 재구현(난수열은 Python 과 다름).
- **동치성**: `../tests/fixtures/shared_cases.json` 사례를 Python·TS 양쪽이 같은 판정·목록으로 통과.
- 단위 테스트의 그래프 fixture 는 `../tests/fixtures/*.yaml`, 학생 A/문제는 `../examples/real/*.yaml` 을 직접 읽어 `src/data` 와 일치하는지 검사한다.

## 상태·저장 (`src/state.ts`)

- 학생 상태는 **명시 기록만** 들고 있다(없는 노드 = 미확인). 명시적 `not_started`는 지우지 않는다.
- 저장(localStorage, 형식 버전 2): `{version, students, currentId, draft}` — 작성 중 문제·확정
  개념·표면 속성까지 복원. 과거 형식은 학생만 이전(빠진 항목 → 미확인). 손상 데이터는 무시.
- IEP 적용은 `applyIepChanges`(선택 항목만) + `undoIepApply`(1회). 저장하지 않는 스냅샷.
- 리듀서·저장 테스트: `src/state.test.ts`.

## 하지 않은 것

LLM 호출, 로그인, 서버, DB, 변이 검사, 진척 지표(진도율·점수·랭킹·레벨), 학생 실명 입력,
라우터, 애니메이션 라이브러리, 다크모드, **그래프 시각화 라이브러리(react-flow·cytoscape·d3 등)**,
그래프 편집 기능. 후보·초안은 룰 기반이며 확정은 교사가 한다. 그래프의 교육학적 변경은
하지 않았다(검토 질문만 `../docs/review/graph_questions.md` 에 기록).
