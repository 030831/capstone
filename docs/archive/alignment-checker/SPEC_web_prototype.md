# 웹 프로토타입 v3 스펙 — "인지적 정렬 검사기" 교사용 화면

작성 2026-11-06 (v0 → v1 → v2 → **v3 2026-11-07**). 목적: 팀 내부 검토·중간 발표 데모. 백엔드 없음, 브라우저에서만 동작.

## 0. v0 → v1 변경 사유 (ComfyUI 오해)

v0는 상단 탭 4개(개념 그래프 / 학생 현행수준 / 문제 검사 / 학급 일괄 검사) 구조였고, **들어오자마자 React Flow + dagre 노드 그래프가 첫 화면**이었다. 사용자가 이전 AI에게 "ComfyUI를 예시로" 언급한 것이 "ComfyUI 형태 노드 그래프를 메인으로 만들라"로 해석된 결과다. 교사가 수업 사이 1~2분에 보는 도구가 노드 에디터가 돼버려 본질을 잃었다.

v1은:
- **상단 탭 제거.** 단일 메인 페이지(문제 검사 위저드)만 남긴다.
- **그래프 뷰 완전 제거.** `@xyflow/react`·`@dagrejs/dagre` 의존성 삭제, `GraphTab.tsx`·`NodePanel.tsx` 삭제.
- **선수관계는 검사 결과 내 인라인 텍스트 트리로.** "그래프에서 보기" 버튼(탭 1 이동) 대신, 결과 카드 안에서 요구 개념 R의 hard 조상을 노드 번호순으로 나열해 보여준다.
- **학생 현행수준·학급 일괄 검사는 헤더 버튼으로 여는 모달.** 메인 흐름을 방해하지 않으면서 필요할 때만 꺼내 본다.

## 0-b. v1 → v2 변경 사유 (사용자 피드백: "여전히 복잡하다")

v1 사용 후 사용자 판정: 그래프 뷰를 없앴는데도 **연구자용이지 교사용이 아니다**. 구체적 불편: ① 문제의 필요 개념을 39개 체크박스 목록에서 직접 찾아 골라야 한다 ② 학생 현행수준을 39행 표에서 일일이 클릭해야 한다 ③ `[2수학01-04]` 근거 코드·`COLLISION` 판정 코드 같은 기술 표기가 화면에 늘 보인다 ④ 결과 카드에 정보가 한 번에 다 보인다.

v2는(당시 판정 엔진은 무변경 — 변화는 전부 입력·표시 계층): 표면을 일상 언어로, 기술 표기는 접기, 개념 선택 = 힌트 제안 + 교사 확정, IEP 문장 붙여넣기 초안, 39행 표는 그룹별 접기.

## 0-c. v2 → v3 변경 사유 (2026-11-07 사용자 지시서)

v2 검토에서 지적된 문제: **"기록 없음"을 "미시작"으로 취급해 왔다.** IEP는 확인한 것만
기록하는 문서이므로, 기록에 없는 개념을 미시작(=교사가 안 다뤘다고 확인)으로 표시하면
미확인과 미시작이 섞여 판정이 거짓으로 단정된다. 또 ① IEP "초안 채우기"가 학생 데이터를
즉시 바꿔버렸고 ② 개념 후보가 자동으로 검사에 반영될 여지가 있었으며 ③ 입력이 불완전한
반 검사가 예시 문제로 자동 대체됐고 ④ 결과 문구가 "지금 딱 맞는 문제"처럼 성공을
보장하는 톤을 썼다. 저장은 조용히 실패했고, 모달은 키보드로 조작하기 어려웠으며,
1,024px 최소 폭으로 좁은 화면에서 쓸 수 없었다.

v3 (지시서 §3~§8 반영, 판정 알고리즘 자체는 §0-c 의 4상태/4판정으로 개정):
- **상태 4종·판정 4종.** `unknown`(기록 없음)과 `not_started`(명시적 미시작)을 구분하고,
  판정에 `NEEDS_REVIEW`(기록을 확인해야 함)를 추가한다(§1-상태 참조, 엔진 스펙
  `docs/SPEC_collision_checker.md` §3 과 동일 의미 — TS 엔진이 Python 엔진과 같은 판정을 낸다).
- **IEP 초안과 확정 데이터 분리.** 붙여넣기 → "변경 내용 미리 보기" → 항목 선택 →
  "선택한 내용 적용" → 1회 되돌리기. 미리 보기만으로 학생 데이터·localStorage·검사 결과가
  바뀌지 않는다. "선수까지 숙달"도 같은 미리 보기 흐름을 탄다.
- **문제 입력 의미 명확화.** "이 문제에서 다루는 개념"(= requires, 선수는 엔진이 계산) /
  "문제에서 찾은 개념 후보"(자동 제안, 반영 안 됨) / "검사에 사용할 개념"(확정) 로 문구 정리.
  개념은 교사가 "개념 확인"을 눌러 확정해야 검사가 실행되고, 문제 글·개념이 바뀌면 확정이 풀린다.
  검사 후 입력을 고치면 결과 카드에 "이전 입력의 결과"로 표시된다.
- **반 검사 가드.** 검사한 문제(확정 스냅샷)만 반 검사에 쓴다. 예시 문제 자동 대체 없음.
  미확인 기록이 있는 학생은 "아직 확인하지 않은 기록"으로 구분해 센다.
- **결과 문구.** 확인·기록 중심 표현만 쓴다("확인이 필요한 선수 개념이 있어요" 등 4종) +
  "선택한 개념과 학생 기록을 기준으로 확인한 결과입니다. 문제 표현과 지원 방법을 함께 살펴보세요."
  노출 순서: 판정 요약 → 확인할 선수 개념/미확인 기록 → 교사 동작(기록 확인·문제 수정·반 검사) → 자세히 보기(접기).
  개발 계획·LLM 예정·판정 코드 같은 구현 설명은 기본 화면에서 제거.
- **저장 v2·접근성·반응형.** 학생 상태·현재 학생·작성 중 문제·확정 개념·표면 속성을
  localStorage 에 복원(형식 버전 2, 과거 형식 이전). 저장 실패는 "이 브라우저에 저장하지 못했어요"
  로 알린다. 모달 포커스 트랩·닫힘 버튼 복귀·배경 inert·Esc. 색이 아닌 텍스트로 상태 구분.
  1,024px 최소 폭 제거, 390/768/1280 확인, 표는 표 영역 안에서만 가로 스크롤.

## 1. 꼭 지켜야 할 제품 원칙 (CLAUDE.md에서 발췌 — 위반하면 반려)

1. 시스템은 "좋은 문제"를 정의하지 않는다. **준비도 판정(COLLISION / NEEDS_REVIEW / ALIGNED / TOO_EASY)**만 한다.
2. **IEP를 진도표로 만들지 않는다.**
   - 학생별 진도율 %, 커버리지, 점수, 랭킹, 레벨 같은 진척 지표 **금지**.
   - outer fringe(지금 배울 수 있는 개념)는 **순서 없는 후보 집합**으로만 표시. "추천 1순위", "다음 단계" 같은 표현 금지. 우선순위는 교사가 고른다.
   - 충돌 판정은 경고이지 처방이 아니다. `suggested_next`는 충돌이 났을 때만, 갭을 메우는 용도로만.
3. AI는 이 프로토타입에 없다. 후보·초안은 **룰 기반**(키워드·숫자 관계)이며 결정적이다. 확정은 어느 쪽이든 **교사가** 한다.
4. 학생은 익명 ID(학생 A, B…)만. 실명·학교명 입력란 없음.
5. **미확인(unknown)을 미시작·미숙달로 표시하지 않는다.** 기록이 없으면 "미확인"이고,
   검사 결과에서는 NEEDS_REVIEW 로 구분해 보여준다.

## 2. 기술 스택

- Vite + React 18 + TypeScript. 상태 관리는 React 내장(useReducer)만.
- **그래프 시각화 라이브러리 없음.** 선수관계는 텍스트 트리로 표시.
- YAML 파싱: `js-yaml`. `graph/graph_v0.yaml`을 **빌드 시 JSON으로 변환**(`scripts/graph-to-json.mjs` → `src/data/graph_v0.json`)하고 앱은 JSON만 import. 원본 YAML은 단일 진실 원천.
- 테스트: `vitest`. 엔진 포팅 테스트 + `draft.ts` 룰 테스트 + 상태(리듀서·저장) 테스트 +
  **컴포넌트 흐름 테스트(실제 화면 흐름)**. 컴포넌트 테스트 환경은 jsdom +
  `@testing-library/react`·`@testing-library/user-event`·`@testing-library/jest-dom`(모두 devDependency —
  UI/상태관리 라이브러리가 아니라 테스트 인프라).
- 스타일: 단일 CSS 파일. Tailwind·UI 킷 금지(의존성 최소화).
- 그 외 런타임 의존성 추가 금지. 번들은 `npm run build` 한 번으로 `dist/`에 생성되어야 하고 `dist/index.html`을 그대로 열어도 동작해야 한다(`base: './'`).

## 3. 엔진 포팅 `src/engine/`

Python `checker/engine.py`와 **동일 의미**로 TypeScript 포팅. 2026-11-07 개정(상태 4종·판정 4종):

```ts
type State = 'unknown' | 'not_started' | 'emerging' | 'mastered';
type Verdict = 'COLLISION' | 'NEEDS_REVIEW' | 'TOO_EASY' | 'ALIGNED';
interface CheckResult {
  verdict: Verdict; requires: string[];
  gapHard: string[]; gapSoft: string[];          // 명시적 미확보만
  unknownHard: string[]; unknownRequired: string[]; // 기록 없음(선수/요구 구분)
  suggestedNext: string[]; unmasteredRequires: string[]; explanation: string;
}
```

규칙(Python 구현과 동일): 판정 순서 COLLISION > NEEDS_REVIEW > TOO_EASY > ALIGNED.
emerging·명시적 not_started는 gap에 포함. unknown은 gap과 분리. suggestedNext 는
gapHard 중 hard 선수가 **실제로 모두 mastered**인 노드만(선수에 unknown 이 있으면 제외),
정렬은 (R까지 hard 최단거리, ID). gapHard/gapSoft/unknownHard 는 ID 오름차순.
`check`는 빈 requires 를 DataError 로 거부한다.

**동치성 검증**: `tests/fixtures/shared_cases.json`(재생성 `scripts/gen_shared_cases.py`)의
사례를 Python 과 TS 양쪽 엔진 테스트가 같은 판정·같은 목록으로 통과해야 한다.

테스트 `src/engine/engine.test.ts`: 스펙 5장 케이스 + 미확인/NEEDS_REVIEW 케이스 +
공유 fixture 25건 + 합성 학생 불변식(완전 확인 학생: M ∪ fringe 밖 노드는 항상 COLLISION,
부분 확인 학생: COLLISION 또는 NEEDS_REVIEW) + 학생 A × 문제 3개 고정 결과.

### 메인: 문제 검사 위저드 (좌우 2단 카드)

**왼쪽 카드 — 문제.** 흐름: `학생 선택 → 문제 작성 → 개념 확인 → 검사`.
- 예시로 채우기 버튼 3개(교사가 직접 고른 것만 반영 — 확정 없이 채워진다).
- 문제 글 textarea.
- **"이 문제에서 다루는 개념"** fieldset:
  - "검사에 사용할 개념:" 선택 칩(× 제거) + **"개념 확인" 버튼 → "개념 확인 완료" 배지**.
    문제 글이나 개념이 바뀌면 확정이 풀리고 검사 버튼이 다시 비활성화된다(표면 속성 변경은 유지).
  - **"문제에서 찾은 개념 후보"** 칩(근거 표시). 후보는 검사에 자동 반영되지 않는다.
    후보 규칙(`src/data/draft.ts`): ① 명시적 수식("8+5", "13−5")과 수량 2개 + 연산 동사가
    함께 있을 때만 숫자 규칙 적용(문항 번호 등은 제외) ② 우선도(수식 3 > 좁은 키워드 2 >
    넓은 키워드 1) 순 상위 6개, 동률만 ID 정렬 ③ "15−3"은 받아내림 아님, "13−5"와 구분
    ④ 합이 10이면 N16, 10을 넘으면 N26.
  - "직접 고르기" 접기(검색 + 그룹 체크박스).
  - 안내문 "후보는 문제 글에서 찾은 초안이에요. 검사에 쓸 개념은 교사가 확인해 주세요."
- 표면 속성 details(수 범위/문맥/표현/지원; 저장만, 판정에 안 씀).
- "{학생 이름} 기준으로 검사" 주 버튼 — `확정 + 개념 1개 이상 + 문제 글` 조건을 모두 만족해야 활성화.

**오른쪽 카드 — 결과.**
- 빈 상태 안내 → 검사 후 결과 카드(verdict별 테두리·배경색, 글자·도형·문구로도 구분):
  1. **판정 요약**: 큰 배지(§7 문구 4종) + 의미 문장 + 범위 안내 문구("선택한 개념과 학생
     기록을 기준으로…") + 이 문제에서 다루는 개념 칩 + 문제 글. 입력이 바뀌었으면 맨 위에
     "이전 입력의 결과예요" 표시.
  2. **확인할 선수 개념 / 미확인 기록**: "아직 확인하지 않은 기록"(선수/이 문제의 개념 태그) →
     "확인이 필요한 선수 개념"(상태 표시) → "있으면 좋은 준비(참고)"(soft) → COLLISION 일 때만
     "지금 바로 다룰 수 있는 개념"(suggestedNext, 순서 없는 후보 안내).
  3. **교사 동작**: "학생 기록 확인"(모달) · "문제 수정하기"(문제 글로 포커스) · "반 일괄 검사".
  4. **"자세히 보기" 접기**: 엔진 설명 문장 + 판정 코드(영문) + 인라인 학습 계보(상태 4종 표시:
     ✓숙달/△형성 중/✗미시작/?미확인 + 근거 코드).
- 금지 문구(스크립트가 자동 검사): "지금 딱 맞는 문제", "도전시키기 좋은 문제", "준비를 메우면 그대로 쓸 수 있음", "반 전체에게 내도 됨", 보장 표현, 진도 표시.

### 모달 1: 학생 현행수준 (v3)

1. **IEP 문장 붙여넣기 → 미리 보기.** textarea + "변경 내용 미리 보기" → 표
   (개념 | 현재 상태 | 제안 상태 | 근거 문장 | 적용 체크) + "선택한 내용 적용".
   - 미리 보기만으로 학생 데이터·localStorage·검사 결과가 바뀌지 않는다.
   - 원문을 수정하거나 학생을 바꾸면 미리 보기가 무효화된다(다른 학생에게 적용되지 않음).
   - **확인 필요 항목**은 상태를 바꾸지 않고 이유와 함께 나열한다: 긍정·부정 혼재 문장
     ("10까지 세기는 할 수 있지만 받아올림은 못함"), "못함"(미시작과 동일시하지 않음),
     어느 개념인지 구분 안 되는 서술("두 자리 수 덧셈" → 받아올림 있/없 확인 필요),
     문장 간 상태 충돌. "도움/구체물" 동반은 형성 중 제안(독립 수행 아님).
   - 적용 뒤 **"적용 되돌리기"**(최근 1회).
2. **그룹별 접힌 표(A~F)**: 상태 4택 세그먼트(**미확인/미시작/형성 중/숙달** — 미확인 선택은
   기록을 지운다), "선수까지 숙달(미리 보기)" 버튼(같은 미리 보기 흐름), 불일치 경고.
3. 하단 note: 상태 정의(미확인 포함 4종) + "이 표의 확정은 교사가 합니다".

### 모달 2: 반 일괄 검사 (v3)

- **검사한 문제**(마지막 검사의 확정 스냅샷 `submitted`)만 사용한다. 작성 중인 초안과
  혼합하지 않는다. 검사한 문제가 없으면 예시로 자동 대체하지 않고 안내만 보여준다
  ("메인 화면에서 문제를 적고 개념을 확인한 뒤 검사해 주세요").
- 상단에 실제 검사한 문제 글·개념 표시. 행=학생, 열=판정 배지 / 확인이 필요한 선수 개념 /
  아직 확인하지 않은 기록 / 지금 바로 다룰 수 있는 개념. 기록이 없는 학생은 NEEDS_REVIEW
  로 구분해 센다("준비됨"으로 세지 않는다). "반 전체에게 내도 된다" 같은 결론 없음.
- 행 클릭 → 그 학생으로 전환 + 메인에서 같은 문제로 상세 결과 보기.

### 상태 관리 (`src/state.ts`)

```ts
type ModalKey = 'none' | 'students' | 'batch';
interface Draft {
  text: string;            // 작성 중인 문제 글
  requires: string[];      // 검사에 사용할 개념(확정 대상)
  confirmed: boolean;      // 교사가 개념을 확인했는지(검사 실행 조건)
  surface: Surface;
}
interface AppState {
  students: Student[];
  currentId: string;
  draft: Draft;
  submitted: { text: string; requires: string[] } | null;  // 검사 시점 스냅샷
  lastApplyUndo: { studentId: string; states: States } | null;  // IEP 적용 1회 되돌리기(저장 안 함)
  modal: ModalKey;
}
```

액션: `selectStudent`, `setNodeState`(unknown → 키 삭제, 명시적 not_started 보존),
`applyIepChanges`/`undoIepApply`, `addStudent`/`deleteStudent`/`resetPresets`,
`setDraft`(text/requires 변경 시 confirmed 해제), `confirmConcepts`, `loadSample`,
`submit`(확정 조건 검사), `openModal`/`closeModal`, `openStudentResult`.
v2의 `applyIepDraft`(즉시 반영)·`masterWithPrereqs`(한 번에 숙달)는 제거되고 미리 보기 흐름으로 대체됐다.

**localStorage (형식 버전 2)**: `{ version: 2, students, currentId, draft }`.
학생 상태·현재 학생·작성 중 문제·확정 개념·표면 속성을 복원한다. 과거 형식(버전 없는
`{students, currentId}`)은 학생만 이전(빠진 항목은 unknown), 초안은 복원하지 않는다.
손상된 데이터는 무시하고 프리셋으로 시작한다. 저장 실패는 조용히 무시하지 않는다
(`saveStored` 가 false 반환 → App 이 경고 표시).

## 5. 인라인 학습 계보 (자세히 보기 접기 안)

요구 개념 R(들)의 hard 조상 합집합 + R 자신을 **노드 번호순**으로 세로 리스트.
각 항목: 마커(◆=이 문제의 개념 / ✓=숙달 / △=형성 중 / ✗=미시작 / ?=미확인), 라벨,
상태 텍스트(4종), 태그(이 문제의 개념/확인 필요/기록 없음 — COLLISION 또는 미확인 표시),
근거 성취기준 코드 1개. 줄 배경: mastered=흰색, emerging=연노랑, 명시적 미시작+갭=연주황,
미확인=연회색.

## 6. 디자인 톤

- 교사가 수업 사이에 1~2분 보는 도구. 차분하고 밀도 있는 업무용 UI. 장식 없음.
- 색: 중립 회색 바탕 + 판정 4색(확인 필요 선수=주황, 기록 확인 필요=앰버, 선수 확인됨=청록,
  숙달 기록=회청). 색만으로 의미 전달 금지 — 항상 텍스트 라벨·도형 동반.
- 작은 회색 글자(`--ink-3`)는 본문 배경 대비 4.5:1 이상(#5d6774, 배경 대비 5.2:1).
- 한국어 UI. 시스템 폰트 스택. 웹폰트 로드 금지(오프라인 데모). 다크모드 불필요.

## 7. 산출물 위치와 검수 기준

- 위치: `web/` (package.json, vite.config.ts, src/, scripts/, README.md)

- `npm run graph:json`은 `../graph/graph_v0.yaml` → `src/data/graph_v0.json`. 생성된 JSON은 커밋 대상.
- README.md: 실행 방법, 화면 설명, 엔진 포팅 주의점, "하지 않은 것".

  ② 금지어 0건 — **발견 시 exit 1**. 사용자가 입력한 문제 글(`[data-user-content]`)과
  제품 고정 문구를 구분해 오탐을 막는다 ③ 모달 포커스(이동·순환·inert·Esc·버튼 복귀)
  ④ 1280/768/390 세 폭에서 페이지 전체 가로 스크롤 없음(표 영역 안 스크롤만 허용).
  스크린샷: tab1~4(1280 주 흐름·학생 모달·반 모달) + w390/w768.
- 컴포넌트 흐름 테스트(`src/components/App.test.tsx`, jsdom+RTL): 문제 확정 흐름·이전 입력
  표시, IEP 미리 보기 불변성·적용·되돌리기·학생 전환·혼재 문장, 반 검사 예시 대체 금지·
  미확인 학생 구분, 모달 포커스, 저장 실패 안내.
