## 1. 한 문단 요약

특수학급 학생은 정해진 커리큘럼이 없어 교사가 학생마다 개별화교육계획(IEP)에 맞춰 문제를 직접 만든다. 이때 가장 흔하고 눈에 안 띄는 실패는 "문제 자체는 멀쩡한데 **이 학생에게는 선수 개념이 빠져 있어** 풀 수 없는" 경우다 — 예컨대 받아올림 덧셈 문제를 냈는데 학생이 아직 '10의 보수'를 모르는 경우. 이 프로젝트는 초등 수학 '수와 연산' 범위의 개념 39개와 선수관계 72개를 **교육과정 원문 근거와 함께** 그래프로 만들고, 교사가 문제의 요구 개념과 학생의 현행수준을 입력하면 `COLLISION(선수 미도달) / ALIGNED(지금 적절) / TOO_EASY(이미 숙달)` 세 가지로 판정한다. 시스템은 "좋은 문제"를 정의하지 않는다. 좋은 문제의 **필요조건**(준비도)만 기계적으로 검사하고, 판단은 교사에게 남긴다. 현재 상태: 그래프 v0 + Python 판정 엔진(CLI) + React 웹 프로토타입(백엔드 없음)까지 완성. AI(LLM)는 아직 한 줄도 안 들어가 있다 — 의도적이다(§3, §10).

## 2. 왜 이 프로젝트인가 — 문제 정의와 논의 과정

이 절은 설계가 왜 이렇게 됐는지 설명한다. 이어서 작업하는 사람이 **같은 함정에 다시 빠지지 않게** 하려는 것이다. 원문 로그는 `docs/review/상담로그_Qwen_2026-11-06.md` (팀 내부 자료, 공개 레포에는 포함하지 않음).

### 2.1 출발점과 배경

- 팀 주제: "특수학급을 위한 학습 웹 서비스". 초기 안(9주차 발표, 서비스명 '늘봄')은 학생용 문제 풀이 + 통계 + AI 문제 생성이었다.
- 배경 조사에서 확인한 것: 특수교사가 외부 자료를 끌어다 쓰는 사례가 많고(저작권 문제), 국립특수교육원의 **열린배움터**(배부·통계·AI 디지털 교육자료)와 민간 **IEPON**(iepon.site — 관찰 기록 → IEP 평가문장 초안 → 나이스 복사, 학습지 제작 메뉴 포함)이 이미 있다.
- IEP(개별화교육계획)는 법정 문서이고, 특수학급 학생은 학생마다 목표가 다르므로 교사의 문제 제작 부담이 매우 크다.

### 2.2 방향을 바꾼 여섯 번의 논의 (요약)

| 라운드 | 제안 | 사용자의 반론·수정 | 남은 것 |
|---|---|---|---|
| 1 | 교사가 원형 문제를 만들고 AI가 개별화 변형 + 승인 큐 | — | "AI는 창작이 아니라 보조" 원칙 |
| 2 | 기능 차별화(1개→N개 변형) | **기능 차별화는 따라잡힌다. 문제의 질로 차별화하고 싶다** | 품질 차별화 |
| 3 | 교육학적 가드레일(CRA, UDL 등)을 UI로 강제 | 좋지만 "품질을 누가 정의하나"가 남음 | — |
| 4 | 문헌 조사 — 우수 문제의 공통 특징 | 확신을 위해 근거 요청 | 문헌 기반 접근 |
| 5 | 교사 인터뷰로 품질 기준 수립 | **교사에게 '좋은 문제가 뭔지' 묻는 것 자체가 오류. 교사마다 다르고, 교사가 좋다고 한 문제가 학생에겐 나쁠 수 있다. 최종 판단은 전적으로 교사. 대학생 신분이라 교사 데이터 수집도 어렵다** | 주관적 평가 배제, 문헌 기반 Rule화 |
| 6 | 가이드라인 준수율을 품질 지표로 | **"지침을 잘 지켰다고 좋은 문제가 되나?"** → 아니다. 지침은 '접근 가능한' 문제만 보장하고 '배움이 일어나는' 문제는 보장 못 한다 | **인지적 정렬**: 문제의 요구 개념 × 학생의 선수 개념 도달 여부 |

최종 결론: **"문제를 만드는 도구가 아니라, 인지적 교량(선수관계)을 검증하는 엔진"**.

### 2.3 그 후 확정된 것 (2026-11-06, 이 레포 작업 중)

- **검사기가 제품이다.** 에디터·변형 엔진은 IEPON 등과 정면 충돌하고 이길 수 없다. 교사가 어디서 만든 문제든 붙여 넣고 학생을 고르면 판정하는 것이 차별점. IEPON의 관찰 기록("수 모형 없이 두 자리 수 덧셈 3/4 해결")은 경쟁 상대가 아니라 우리 시스템의 **입력**(노드 상태 갱신)이 될 수 있다.
- **이것은 새로운 아이디어가 아니라 기존 분야의 적용이다.** Knowledge Space Theory(Doignon & Falmagne; ALEKS의 기반), Q-matrix, Clements & Sarama의 Learning Trajectories가 그것이다. 발표에서 이를 숨기지 말고 "KST의 outer fringe를 특수교육 IEP에 적용했다"로 포지셔닝한다. 차별점은 알고리즘이 아니라 (a) 특수교육 기본교육과정까지 덮는 그래프, (b) IEP 현행수준을 입력으로 받는 것, (c) 교사가 만든 문제를 검사하는 것.
- **가치가 생기는 조건: 교사가 이미 아는 걸 반복하면 가치 0.** "덧셈 전에 수 세기"는 모든 교사가 안다. 가치는 성취기준보다 한 단계 아래에서 생긴다 — 받아올림을 못 하는 학생이 '10의 보수'가 안 되는 건지 '십몇=10과 몇'이 안 되는 건지 짚어 주는 것. 그래서 노드를 그 수준으로 쪼갰다.
- **RAG는 필요 없다.** 그래프는 노드 수십 개짜리 구조화 데이터다. LLM이 필요한 자리는 셋뿐이고 모두 구조화 출력이다: 문제 텍스트 → 요구 노드 태깅, IEP 현행수준 문장 → 노드 상태 추출, 충돌 시 스캐폴딩 문장. 모두 JSON schema 강제 + 교사 확인.
- **교육 전문성 부족은 '근거 달린 데이터 큐레이션'으로 대체한다.** 그래프의 모든 노드·엣지에 교육과정 원문 쪽수 또는 학습궤적 레벨명을 붙인다. 로더가 근거 없는 엣지를 거부한다. 설계자의 주관을 배제하기 위한 장치이고, "너희가 교육을 아느냐"는 질문에 "저희 판단이 아니라 이 문헌의 판단을 코드화했다"로 답하기 위한 것이다.
- **대상 교육과정은 공통교육과정 + 특수교육 기본교육과정 둘 다.** 1차 자료(교육부 고시 제2022-34호 총론 별책1 p.27~28, `sources/2022_특수교육_교육과정_총론_편성구조_발췌.md`)에 따르면 특수교육 교육과정은 "공통·선택중심 교육과정"과 "기본 교육과정"으로 편성되고, 기본교육과정의 정식 대상은 특수학교 학생이지만 일반학교 특수학급 학생도 "특수교육 교육과정의 교과(군) 내용과 연계하거나 대체하여 운영할 수 있다"(버-3). 즉 특수학급 교사의 IEP에는 두 교육과정의 내용이 모두 나타날 수 있다. 두 교육과정은 **같은 개념 사다리를 다른 속도로** 오른다 — 공통 1~2학년군의 "두 자리 수 덧셈·뺄셈" 하나가 기본교육과정에서는 초3~4(한 자리 수) → 초5~6(10의 보수, 몇십) → 중(받아올림) → 고(받아내림)로 펼쳐진다. 그래서 노드는 개념 단위로 하나만 두고 두 교육과정의 성취기준 코드를 함께 태깅한다.
- **IEP는 진도표가 아니다** (현장 교사 블로그 '교육과정 VS 개별화교육계획', https://blog.naver.com/jamin96/224452526177 — 원문 사본은 레포에 포함하지 않음). IEP는 교육과정 진도를 따라가는 문서가 아니라 그 학생에게 가장 시급한 핵심 기술 하나(예: '글자 읽기')에 집중하는 문서다. 우리 도구가 "다음에 배울 노드"를 순서대로 보여 주면 교사를 진도표 오류로 밀어 넣는다. 그래서 §3의 원칙이 생겼다.

### 2.4 이전 작업(`../project` 폴더)과의 관계

이 레포 이전에 같은 팀이 11/3~11/5에 다른 AI들과 조사한 자료가 별도 폴더에 있다(이 레포에는 없음). 그 자료의 결론은 "중·고등 특수학급 경증 학생, 생활 경제 수학, AI 문제 생성(정답 보장)"으로 **현재 방향과 다르다**. 신뢰도 평가와 모순점은 `docs/review/prior_research_review.md`에 정리했다. 거기서 가져올 만한 것은 IEP 목표 문장 28개(`goals.csv`, 호미·교육청·NISE 출처)뿐이고, 이는 §10의 "현행수준 → 노드 상태 추출" 테스트셋으로 쓸 예정이다.

## 3. 제품 원칙 (바꾸지 말 것)

사용자가 명시했거나 논의 끝에 확정한 원칙. 코드 리뷰·기능 추가 시 이것에 비춰 판단한다.

1. **좋은 문제는 사람(교사)이 만든다. AI는 보조.** 시스템은 문제를 창작하지 않는다.
2. **기능 차별화가 아니라 품질 차별화.**
3. **교사에게 "좋은 문제가 뭔지" 묻는 방식은 오류.** 설문·인터뷰로 품질 기준을 세우지 않는다.
4. **"정말 좋은 문제인가"의 최종 판단은 전적으로 교사.** 시스템은 필요조건만 검사한다.
5. **가이드라인 준수 ≠ 좋은 문제.** 인지적 정렬(준비도)이 핵심.
6. **현실 제약:** 대학생 신분이라 실제 교사 데이터 수집·설문은 어렵다. 검증은 문헌 근거 + 합성 데이터 + 특수교육과 학생 휴리스틱 평가로.
7. **IEP를 진도표로 만들지 않는다.**
   - 학생별 진도율 %, 완료율, 커버리지, 점수, 랭킹, 레벨 같은 진척 지표 **금지**. "12/39" 같은 카운트도 금지.
   - outer fringe(지금 배울 수 있는 개념)는 **순서 없는 후보 집합**으로만 표시. "다음 단계", "1순위", "추천 순서" 금지. 우선순위는 교사가 고른다.
   - 충돌 판정은 **경고**("지금 내면 안 됨")이지 **처방**("다음엔 이걸 내라")이 아니다. `suggested_next`는 충돌이 났을 때만, 갭을 메우는 용도로만 나온다.
   - 웹 프로토타입의 `web/scripts/screenshots.cjs`가 UI 전체 텍스트에서 금지어를 자동 검사한다.
8. **학생 개인정보.** 학생은 익명 ID만. 실명·학교명 입력란 없음. 향후 LLM에 보낼 때도 현행수준 텍스트만 익명화해서 전송.
9. **근거 없는 엣지는 없다.** 그래프 로더가 `sources`가 빈 노드·엣지를 거부한다.

## 4. 시스템 구조와 레포 구성

```
문제 텍스트 ──(교사가 요구 개념 태깅; 향후 LLM 초안 + 교사 확인)──► requires: [노드 ID]
                                                                          │
IEP 현행수준 ──(교사 입력; 향후 LLM 초안 + 교사 확인)──► states: {노드 ID: 3단계}   │
                                                                          ▼
                                          graph_v0.yaml ──► 판정 엔진 ──► COLLISION / ALIGNED / TOO_EASY
                                          (39노드·72엣지)                 + gap_hard, gap_soft, suggested_next, explanation
```

| 경로 | 내용 | 상태 |
|---|---|---|
| `graph/graph_v0.yaml` | **인지 의존성 그래프 v0.** 단일 진실 원천. 39 노드, 72 엣지(hard 61 / soft 11). 모든 노드·엣지에 `sources`(교육과정 코드·쪽수 / 학습궤적 레벨명) | 완료, DAG 검증 통과 |
| `sources/` | 그래프 근거 1차 자료 3종. 국가교육과정정보센터(ncic.re.kr) PDF에서 직접 추출한 **원문**, 쪽수 포함 | 원문 확인 완료 |
| `checker/` | Python 판정 엔진 + CLI. `models.py`(pydantic 스키마), `loader.py`(YAML→그래프, 검증), `engine.py`(판정), `explain.py`(한국어 설명 템플릿), `cli.py` | 테스트 23개 통과 |

데이터 모델 (3개 파일 형식, YAML):
- **그래프** `nodes[{id, label, description, level_hint, sources[]}]`, `edges[{from, to, kind: hard|soft, sources[]}]`
- **학생** `states: {노드ID: mastered | emerging | not_started}` (명시 안 된 노드는 not_started)
- **문제** `requires: [노드ID]` + `surface{number_range, context, representation, support}` (표면 속성은 v1 변이 검사용, 지금은 저장만)

## 5. 핵심 알고리즘

```
R  = problem.requires                       (문제가 요구하는 개념)
M  = {n | state[n] == mastered}             (학생이 도달한 개념)

P_hard(R) = R의 모든 hard 엣지 조상(이행적 폐포), R 자신은 제외
P_soft(R) = R의 soft 엣지 직접 선수 (1단계)

gap_hard = P_hard(R) − M
gap_soft = P_soft(R) − M

if gap_hard ≠ ∅ : COLLISION    ← 선수 미도달. 경고.
elif R ⊆ M      : TOO_EASY     ← 이미 숙달. 연습용.
else            : ALIGNED      ← 선수는 모두 도달, R 자체는 미도달/진행중 = 근접발달영역(ZPD)

suggested_next = gap_hard ∩ outer_fringe(M)   (충돌일 때만)
  outer_fringe(M) = mastered가 아니면서 hard 선수가 모두 mastered인 노드
                  = KST의 outer fringe = "지금 바로 배울 수 있는 것"
  정렬: (R까지 hard 최단거리, ID) — 표시할 때는 순서 의미 없음(원칙 7)
```

- `emerging`(형성 중)은 mastered가 아니므로 gap에 포함된다.
- 불변식(테스트 9번): 학생 상태가 하향 폐쇄(어떤 노드가 mastered면 그 hard 조상도 모두 mastered)일 때, 문제 노드가 M ∪ outer_fringe에 속하면 COLLISION은 0건이고, 그 밖의 노드는 항상 COLLISION이다. 합성 학생 100~200명 × 모든 단일 노드 문제로 검사한다.
- 설명 문장은 템플릿이다(LLM 없음). 예: *"이 문제는 '받아올림 있는 (몇)+(몇)'을 요구하는데, 학생은 선수 개념 '10의 보수', '십몇 = 10과 몇'이 미도달입니다. '10의 보수'은(는) 지금 바로 다룰 수 있는 선수 개념입니다."* 처방 톤("~부터 다루는 것을 권장합니다")은 의도적으로 뺐다.

## 6. 개념 그래프 v0 — 설계 결정과 근거

### 6.1 범위
초등 수학 '수와 연산' 중 **수 이전 개념(일대일 대응) ~ 두 자리 수 받아올림 덧셈·뺄셈, 곱셈구구**. 화폐·측정·시각은 범위 밖(기본교육과정에서 화폐는 '수와 연산' 영역에 속하지만 v0에서는 제외).

### 6.2 그룹 (노드 ID 접두 번호로 구분)
| 그룹 | 노드 | 내용 |
|---|---|---|
| A 수의 기초 | N01~N04 | 일대일 짝짓기, 직관적 비교, 순서짓기, 작은 수량 즉각 인식 |
| B 수 세기 | N05~N13 | 수 단어 암송, 5/10까지 세기, 수만큼 꺼내기, 숫자 읽고 쓰기, 0, 크기 비교, 순서수, 이어 세기 |

| D 덧셈·뺄셈 | N18~N27 | 의미, 합 5 이하, 합 9 이하 + 식, 0, 덧셈·뺄셈 관계, 10에서 빼기, **받아올림 (몇)+(몇)**, **받아내림 (십몇)−(몇)** |
| E 자릿값 | N28~N36 | 10의 개념·몇십, 두 자리 자릿값, 100까지, 두 자리 비교, 몇십±몇십, 두 자리 ± (받아올림 없음/있음), 세 수 덧셈, □ 식 |

### 6.3 근거 유형
- `curriculum_basic`: 2022 개정 특수교육 기본교육과정 수학 `[N수학01-xx]` (N = 2, 4, 6, 9, 12 = 학년군 끝 학년). 원문: `sources/2022_특수교육_기본교육과정_수학_수와연산_성취기준.md`
- `curriculum_common`: 2022 개정 공통교육과정 수학 `[2수01-xx]`, `[4수01-xx]`. 원문: `sources/2022_공통교육과정_수학_수와연산_성취기준.md`
- `trajectory`: Clements & Sarama 학습궤적(learningtrajectories.org 현행 레벨명). **레벨 이름과 순서만 원문 확인**했고 레벨 설명은 미확인. 레벨↔노드 대응은 설계자 판단.

### 6.4 hard / soft 기준
- **hard**: 원문 해설이 선수관계를 명시한 경우. 예: `[9수학01-07]` 해설 "받아올림이 있는 (몇)+(몇)은 **10의 보수 개념을 바탕으로**" → `N16_ten_complements → N26_add_single_digit_carry` hard.
- **soft**: 배치 순서나 궤적 인접성만 있는 경우. 예: 직관적 비교 → 수 크기 비교.
- 이행적으로 중복인 hard 엣지 4개(예: N16→N26는 N16→N17→N26로도 도달)는 각각 독립된 원문 근거가 있어 **의도적으로 유지**. 판정에는 영향 없다.

### 6.5 세분화의 논리
교육과정 성취기준 한 개가 노드 여러 개로 쪼개진 곳이 많다. 쪼갠 근거는 대부분 기본교육과정 해설의 "단계적 지도" 문장이다. 예: `[4수학01-08]` 해설 "우선 합이 5 이하가 되는 덧셈부터 시작하여 합이 9 이하인 덧셈까지 단계적인 내용을 다룬다" → N19(합 5 이하)와 N21(합 9 이하)로 분리. 현장 블로그의 '글자 읽기' 예시(국어 전체가 아니라 핵심 기술 하나가 IEP 목표)도 같은 수준을 가리킨다.

## 9. 알려진 한계와 열린 질문

- **그래프는 세 사람의 문헌 해석이다.** 교육과정 해설 인용은 정확하지만, "이 해설이 이 엣지를 뒷받침한다"는 판단은 설계자가 했다. 특수교육 전공자가 보면 틀린 엣지가 있을 수 있다. 검토 방식은 "좋은 문제가 뭐냐"가 아니라 **"틀렸다고 보는 엣지만 표시해 달라"**로 한다(원칙 3·6).
- **학습궤적 레벨 설명 미확인.** learningtrajectories.org에서 레벨 이름만 가져왔다. 구판(8단계)과 현행(12단계) 이름이 달라 섞어 쓰면 안 된다(`docs/review/sonnet_web_collection_log.md`).
- **3단계 상태 모델의 한계.** 실제 숙달은 연속적이고 문맥 의존적이다. BKT 같은 확률 모델은 v1 이후 검토. 지금은 단순함을 택했다.
- **요구 개념 태깅은 교사 수동.** 문제 하나에 어떤 노드를 붙일지가 판정을 좌우하는데, 이 단계가 아직 수동이다. LLM 초안 + 교사 확인이 §10의 1순위.
- **변이(variation) 검사 미구현.** 인지 정렬은 "시도할 수 있는가"(준비도)만 본다. "풀 가치가 있는가"는 별개 문제이고, 변화 이론(Variation Theory)에 따라 같은 심층 노드를 공유하는 문제 세트가 표면 차원(숫자·문맥·표현·지원) 중 2개 이상 달라야 통과하는 규칙을 두기로 했다. `surface` 필드는 그 자리다.
- **열린 질문:** (a) 기본교육과정의 화폐 영역을 그래프에 넣을 것인가(IEP 목표에 자주 나옴). (b) 학급 일괄 검사에서 "충돌 N명" 집계는 원칙 7에 위배되지 않는가(현재 판단: 학생 간 비교가 아니라 사전 지원 대상 파악이므로 허용, 단 순위 금지). (c) 교사가 그래프 자체를 수정할 수 있게 할 것인가(근거 필수 원칙과 충돌).

## 11. 작업 규칙 — 이어서 작업하는 사람에게

- **`CLAUDE.md`를 먼저 읽는다.** 사용자가 지시·지적한 내용이 누적되어 있다. 지시가 추가되면 거기에 기록한다.
- `graph/graph_v0.yaml`이 그래프의 **유일한 원본**이다. `web/src/data/graph_v0.json`은 `npm run graph:json`으로 생성되는 파생물이므로 직접 고치지 않는다. 그래프를 고쳤으면 `python -m checker validate`와 `npm run graph:json && npm test`를 돌린다.
- 엣지를 추가할 때는 `sources`에 **원문 인용과 쪽수**를 넣는다. 기억으로 쓰지 말고 `sources/`의 발췌문에서 복사한다. 거기 없는 근거면 먼저 `sources/`에 원문을 추가한다.
- Python 엔진과 TS 엔진은 **같은 의미**를 유지한다. 한쪽을 고치면 다른 쪽도 고치고 테스트 케이스를 양쪽에 추가한다. 설명 문장 템플릿도 동일하게.
- UI 문구를 추가할 때 `web/scripts/screenshots.cjs`의 금지어 검사를 돌린다. "다음 단계" 같은 로드맵 표현도 걸리므로 "앞으로는" 등으로 쓴다.
- 의존성: Python은 networkx / pyyaml / pydantic만. 웹은 react / react-dom / js-yaml / vite / typescript / vitest만. **`@xyflow/react`·`@dagrejs/dagre`는 v1에서 제거됨** (ComfyUI 형태 그래프 뷰를 없애고 교사용 폼·모달 UI로 바꿈). 늘릴 때는 이유를 PR에 쓴다.
- 학생 실명·학교명은 어떤 파일·로그·프롬프트에도 넣지 않는다.
- 이 README의 §2·§3은 **왜**를 기록한 것이다. 기능을 바꾸기 전에 그 변화가 §3의 어느 원칙과 어떻게 관계되는지 한 줄이라도 적는다.

| 현행수준 | IEP의 "지금 이 학생이 할 수 있는 것" 서술. 우리 시스템에서는 노드별 3단계 상태로 구조화 |
| 특수교육 교육과정 | 교육부 고시 제2022-34호. 공통·선택중심 교육과정(별책2) + 기본 교육과정(별책3)으로 편성 |
| 기본교육과정 | 장애 정도가 심한 학생용 별도 교육과정. 정식 대상은 특수학교 학생이나 특수학급에서도 연계·대체 운영 가능 |
| 특수학급 | 일반학교 안에 설치된 특수교육 학급. 이 프로젝트의 1차 사용자(특수학급 교사) |
| 인지적 정렬 (Cognitive Alignment) | 문제가 요구하는 개념의 선수 개념을 학생이 모두 도달했는가. 이 프로젝트의 핵심 검사 |
| 충돌 (Collision) | 선수 개념 미도달 상태에서 그 문제를 내는 것 |
| outer fringe | KST 용어. 현재 지식 상태에서 바로 학습 가능한 개념 집합 = ZPD를 집합으로 정의한 것 |
| 하향 폐쇄 (downward closed) | 어떤 노드가 mastered면 그 hard 조상도 모두 mastered인 상태 집합. KST의 knowledge state 조건 |
| hard / soft 엣지 | 필수 선수(원문 해설에 명시) / 권장 선수(배치 순서·궤적 인접성) |
| ZPD | 근접발달영역(Vygotsky). 혼자는 못 하지만 도움받으면 할 수 있는 범위 |
| 변화 이론 (Variation Theory) | 같은 개념을 표면이 다른 여러 사례로 접해야 개념의 핵심이 분리된다는 학습 이론. v1 변이 검사의 근거 |
| IEPON / 열린배움터 | 각각 민간 IEP 기록 워크스페이스 / 국립특수교육원 온라인 교육 시스템. 경쟁이 아니라 상류(입력)·하류(배부) 관계로 포지셔닝 |
